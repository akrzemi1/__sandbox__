Nathan:


If it is implementation-defined, an implementation is free
to say it is undefined. If you are sure you don't want it
undefined, making it implementation-defined doesn't get you
there.

Generally, listing all the permissible outcomes is the only
way to have a say in what happens. For most things, we list
just one permissible outcome. We can say it is unspecified
which happens. To encourage implementers to pick one, we can
say the choice is implementation-defined, but an implementer's
definition can be just "unspecified".

Implementation definitions are not generally useful because
you may not know which implementation will be used tomorrow
to compile your code. An implementation is free to change their
definition from one release to the next, from one target to
the next, and from one compiler command line option to the
next.

Implementations are also free to define anything the Standard
identifies as undefined, or even fails to identify as defined,
and they do. Most usually that definition is extremely vague,
on the order of "it will do what you would expect if you were
to think it through". Any significant program relies on dozens
or hundreds of those.

When we are lucky, they have referred to some other Standard,
such as Posix. That way, when we `mmap` a file and point a
struct pointer at what was mapped, we rely on their implied,
if vague, definition to trust that the lifetimes of all the
pre-cooked objects we care to point at in the mapped memory
have already begun; that works mostly just because optimizers
can't definitively say they haven't.
