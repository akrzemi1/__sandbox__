== Discussion

=== Zero size is often valid input

While the idea of "invalid input" overlaps with the observation "nobody ever needs to pass this value", 
thery are not the same and there are good reasons to allow "suspicious" values as long as the behavior
of the function can be meaningfully scaled to cover that input. This is often the case when we are taling about ranges
of size zero. Consider https://en.cppreference.com/cpp/string/byte/memcpy[`std::memcpy`]. It takes two pointers and a size. 
It has a precondition that neither of these pointers is a null pointer. 
This seems reasonable at first glance: how could copying even work when you cannot dereference either pointer?
But you do not need to dereference any pointers when the size of the range to copy is zero. But who would
ever request the copying if they new the size was zero? The answer is: sometimes you do not know the size of the range you want to copy:

[source,cpp]
----
void cap_replicate(inplace_vector<byte, 1024>& target, vector<byte> const& source)
{
  size_t size = min(source.size(), 1024);
  target.resize(size);
  memcpy(target.data(), source.data(), size);
}
----

Note that in an empty `vector` `.data()` is a null pointer, and would cause undefined behavior (UB) 
in function `cap_replicate` for no good reason. This is why the precondition in `std::memcpy` is wrong. 

Accepting suspicious-but-valid zero-size input may warrant a branch in the function, as is the case for ASIO's type requirements https://www.boost.org/doc/libs/latest/doc/html/boost_asio/reference/AsyncReadStream.html[`AsyncReadStream`]. The read operation
guarantees that it only resumes the suspended operation when there is either an error to report or at least one byte read. 
The guarantee is different when a zero-sized buffer is provided. In that case the function returns immedialtely with the information
about zero bytes read. One could ask, what the point is in calling the read function with a zero-sized buffer.
The answer: the buffer size (and the expected message size) may be obtained dynamically from reading the previous message.
Sending "size zero" is a legitimate way of saying, "I have nothing more to send", and the user should not be forced to 
put a branch in their code for a special value.


=== Why not runtime-enforce preconditions? 

Some preconditions can be declared, but they can never be runtime-checked. 
For instance, when a function takes a pointer argument with the intention 
to dereference it, there is no way to tell if the pointer points to valid,
type-compatible memory.

Even if a funciton could runtime-check whenther its precondition is satisfied,
as the first thing in its body, it may be a bad idea to force all implementations
to do this. One reason is performance. Consider a binary search function. It has
a precondition that the iput sequence is sorted with repsect to the predicate.
Runtime-checking it is conceptually simple, you just need to perform a linear algorithm.
But when you force implementations to perform a linear algorithm in a function that 
advertizes logarithmic complexity, you break the the function's contract.

This is an extreme example. But even in the cases were the computational complexity is not 
changed, forcing all implementations to penalize users who make sure they call their functions
correctly removes the implementaiton freedom and may compromise the performance requirements
of user programs.

Even in the cases where the runtime-check imposed on the implementations 
has negligible runtime cost compared with the function execution time,
there are reasons to keep the precondition.

Supposing that all implementaitons are forced to runtime-check the condition,
what are they supposed to do when they discover it has been violated?

Abort the program? Many consider it a reasonable "safe" default. But some domains
consider it unacceptable to kill the program only because it is runtime-confirmed 
to be incorrect.

Report "error" via an exception or special error-code object or `std::expected`?
But all these error recovery mechanism work under the assumption that a correct
program correctly responds to a forseen, adverse state in the environment.
These assumptions no longer hold when we are dealing with a provably buggy program.

    pointing to dead memory.

The definition of a precondition (strictly sppeaking, of the __Preconditions:__ clause) 
in the standard library is that if a function is called and any of the preconditions is violated
the behavior of the program is undefined. This is also partially the case with hardened preconditions.
The potential to trigger undefined behavior (UB) causes concerns for some. So why even have them?

 1. Sometimes there is no other way. When a function takes a pointer argument 
    with the intention to dereference it, there is no way to tell if the pointer is valid.
    The only thing to do is to trust that the caller made sure that the pointer is not
    pointing to dead memory.
